One-time passwords on Freenet

Continuous OTP time uses a hardened pulse tip: age-eligible (and seal-reputation-weighted) pulses, not the raw public median. A jump guard holds the last tip if the map leaps more than ~3 bins. Still early MFA — lead-by-example hardening, not a finished adversary model. Digits are TOTP over that tip. Limits: Trust & security.

Algorithm

This is TOTP (time-based), not a counter HOTP product. RFC 6238 defines TOTP by reusing the HOTP truncate as an inner function: 

TOTP(K, T)  =  HOTP(K, C)
C           =  floor(T / X)     // X = 30s bin
T           =  Kairos hardened pulse tip (ms)
K           =  shared secret

So when you see HOTP(K, floor(T / 30s)), that is the TOTP definition — C comes from network time T, not from “press button / increment counter” (true HOTP, RFC 4226 alone). Naming the scheme TOTP is correct; HOTP in the formula is only the HMAC-SHA1 truncate step.

Authenticator vs verify

  1. Share a secret out of band.
  2. Authenticator Subscribes to Kairos (Get + subscribe: true). On UpdateNotification it re-reads state and updates its hardened-tip belief.
  3. Verify does an independent Get when checking a code (same contract, separate read).
  4. Both compute TOTP from their belief. Verifier accepts epochs with enough probability mass under its σ window (staleness widens σ; point estimate t only moves when the tip updates).

Belief (why codes don’t coast on laptop time)

  • Point estimate t = last adopted hardened tip (frozen until Subscribe/Get refreshes it).
  • Local clock only widens uncertainty σ with age since that tip — it does not advance t.
  • Digits change when a new tip moves t across a 30s network-time bin (or belief mass shifts).

What moves the tip

Someone must pulse (site network duty / another client). A Get alone never advances the map. The OTP client prefers aged, reputation-eligible pulses (weighted median); if too few are available it bootstraps from all pulses with wider uncertainty. A sudden multi-bin leap vs the last tip is held (pulse-hold). With one witness, the tip is essentially that witness’s last wall_ms.

Lab UI

The OTP page shows authenticator (Subscribe + code) beside verify (separate Get). Not production MFA by itself — the shared secret must stay secret; tip hardening is example-grade resistance to casual Sybil pulse floods, not a security guarantee.

Why not sealed stamps for this lab? Stamps notarize a specific content hash once ≥5 distinct peers observe. OTP needs a continuously updating time source — the pulse map. Using seals for every 30s epoch would mean opening a new stamp each bin and waiting for five aged peers; that is the wrong tool. Use seals when you need a portable “this hash around this interval” proof.
