Pulses vs stamps

Two surfaces share the same contract. Pulses keep the network warm. Stamps notarize “this content existed around this time” with many distinct witnesses.

Pulse (keep-alive)

A pulse is a signed observation: “this witness key is alive and saw wall time T.” Anyone can pulse. Effects:

  • Updates pulse[node_id] (latest reading).
  • Accrues roster age (and later seal-history reputation) for Sybil friction on stamp observes.
  • Never creates a sealed stamp by itself.

Telemetry’s “Median pulse” is the median of those live readings (client-side). Useful telemetry. Sybil-floodable if treated as truth — see Trust & security. The OTP lab uses a hardened tip (aged + reputation-weighted), not this raw median. Witness bars: longer = closer to the telemetry median.

What a stamp request is

A stamp is not a free-floating clock tick. An app that cares about a specific piece of data asks the network: “when do aged peers think now is, for this content?”

  1. App hashes something it cares about (commit, disclosure, message id, …) → content_hash, picks a unique nonce, calls open_stamp. That creates open_stamps["hash:nonce"] — an open request.
  2. Age-eligible witnesses (~1h on roster; once a few seals exist, also above a seal-history reputation floor) each call observe_stamp with their signed wall time for that request id. The contract stores at most one observation per node_id (a map keyed by pubkey). The same peer cannot fill five slots; re-observing overwrites their one row.
  3. When ≥ 5 distinct eligible observations remain after MAD outlier filtering, the contract seals: weighted median of those wall times (age ramp × reputation), error / [earliest, latest], witness list, transcript digest. Included vs MAD-dropped keys update roster seals_included / seals_outlier. The request leaves open_stamps and lands in sealed_stamps. Further observes on that id are no-ops.

More than five is fine (up to a large per-request cap). Five is the minimum to seal, not a maximum. Extra distinct peers tighten / corroborate the median; they do not reopen a new stamp automatically.

Why median / interval?

Each witness reports its own clock. The seal’s point estimate is a reputation- and age-weighted median of MAD survivors (robust to a few liars or skewed clocks; sustained outliers lose weight over seals). error_ms and [earliest, latest] bound how wide that agreement was at seal time. Apps later widen error with local Get staleness. That is the notarize surface — “this hash was sealed in this window by these keys” — see Notary receipts.

Who opens stamps?

Duty keeps a deterministic public example open (kairos.public.example.v1:v1) so the lab always has a stamp request to show; if pruned, the same id is re-opened. Telemetry / network duty observe open requests; they do not invent arbitrary app content — only this fixed example (plus real app opens).

Which clock for which job?

  • Continuous OTP / live UI — hardened pulse tip (OTP), not raw public median. Seals are discrete notarize events; they are a poor ticking second-hand unless an app opens a new stamp every epoch (heavy, needs ≥5 peers each time).
  • Notarize / portable proof — sealed stamp + receipt.
  • Telemetry — pulse map + help observe any open requests; show sealed list when apps have opened stamps.
Trust model in one line: 5+ different aged keys with seal-history reputation, each signing once per request — not one peer repeating itself, and not the live pulse majority. Details: Trust & security.
